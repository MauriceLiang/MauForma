# RepoVantage 任务中心截图审核 · 2026-11-04

**证据范围：用户上传的一张 Safari 截图**，展示 RepoVantage 任务中心；该截图不是项目源代码，不能证明任务数据、重试动作、过滤逻辑、后台持久化与滚动实现已经正确。

## 截图可见问题

- 主内容呈**长期双列**：左侧一张“任务状态”卡（进行中 3、需要关注 3、已完成 1），右侧大型“任务记录”列表（标示 7 项），状态数字仅占小部分面积，却永久占据较宽垂直栏。
- 每条任务记录有图标、仓库、状态徽章、类型/相对时间、一句当前阶段，之后又重复“进度百分比未知，当前显示阶段状态”，导致一眼扫描耗时。
- 左侧状态统计没有明显充当**筛选控件**；右侧缺少清晰的状态/时间/操作列，列表虽宽却并不利于比较哪项需要处理。
- 任务不止一种：运行、排队、部分覆盖、需处理、完成和分析中等。不同状态需要不同动作，而不是简单地把“重试”按钮放在所有非完成行。
- `分项拉取 · 已处理 1,200/6,800 条` 是有数值分母的具体进展，但另一条“统计分位数 · 3 / 7 条”究竟是否总量完成度需理解业务含义；通用的“百分比未知”重复说明不能替代数据契约。
- 右侧多数任务行右半存在大块空白，布局密度与信息密度不匹配。不能通过单纯增大字体/换卡片颜色改善任务可读性。

## 设计建议

1. 将左侧统计转为顶部紧凑且**可点击的状态筛选项**（可含总数/需要处理/运行/等待/已完成），与搜索或排序同一工具区。
2. 主区域使用明确对齐的**任务行**：对象/任务类型、状态、进度或当前阶段、更新时刻、可执行操作。任务标题不要重复三段模糊说明。
3. 对真正处于运行中的分项数据展示有依据的数量和进度；对不可量化阶段直接显示“正在分析 / 查看执行详情”，而不是硬塞 0% 或重复百分比说明。
4. 对失败/部分覆盖显示简洁原因及下一步动作；详细失败堆栈、日志、触发信息放二级详情。
5. 状态分组让用户先找到异常与进行中的内容；历史完成记录可以排序/筛选查看，不默认消耗过多首屏。
6. 窄屏降成任务卡/两行结构，仍保留状态、最近更新、数量和操作；自然滚到底。
7. 检查数据/操作权限后再决定是否展示重试/取消；示例中的“重试”必须明确是本地模拟，不可宣称真实作业已成功重启。

## 不能仅凭截图认定的内容

- 左侧三个统计数字是否可以点击过滤；
- 后端是否在自动推送任务进度；
- 是否真正存在完整日志/错误详情；
- 重试按钮是否安全和有效；
- 相对时间是否准确；
- 任务详情、键盘焦点与手机断点是否实现。

建议结构是**依据可见截图的临时设计方向**，不是 RepoVantage 业务功能已完成或用户已确认的新视觉稿。

## 反例到正确方向

`左侧大状态卡 + 大面积空任务行 + 每条重复说明`
→ `紧凑状态筛选 + 工具栏 + 一致列布局的任务记录 + 可按需深入的详情`。

具体取舍应依用户已确认的配色与导航，不擅自复制 GitHub Actions/Trigger.dev/Linear 的视觉风格。
