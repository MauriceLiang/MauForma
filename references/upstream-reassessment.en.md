# Upstream Skill Reassessment — Coverage, Limits and Non-Transfers

> Reviewed against the 14 design Skills credited by MauForma on 2026-11-20. This document describes **observed upstream practices and independent MauForma decisions**, not copied instructions, an upstream endorsement, or proof that all upstream code can be used. Original upstream repositories, authors and licenses are linked centrally in [README](../README.md#design-skills-and-methodology). The current repository provides Web product guidance rather than a universal design taste score.

## Summary

The new English entrypoint covers most major design gates, but **English source terminology, Chinese specialist prose, actual tooling and success status can still diverge**. Upstream examples are often written for a specific Agent host, a React version, marketing pages, a screenshot-only demo or a special asset tool. Their constraints must be carried over **only with their context**. A documentation reference is not the same as a runnable adoption.

## Highest-risk translation and scope ambiguities found

1. **Instruction routing ≠ run everything**. “Read 1–3 references” must mean start with **one primary guide**, add only specific secondary guides, with an evidence-based exception. The reference table is an index, not 30 required checks. A single guide can serve multiple outcomes. A complex user task can justify more than three.
2. **“Component library first” ≠ install without permission**. For real interactive work inspect the existing stack first. If new dependencies are necessary, the user may delegate project dependency changes as part of the implementation; respect explicitly frozen dependencies, security constraints and host/global settings. Do not silently install a new UI library for a one-line review or a static page.
3. **“Only on request” ≠ only exact literal wording**. Optional Liquid Glass or cinematic effects may follow an explicit design brief or inherited, approved visual system; they must not be added just because a reference Skill uses them.
4. **“Review” ≠ “Fix”**. Formal design critique on review-only tasks does not authorize editing. Small fixes require scoped testing, not a mandatory separate design council. Large visual changes benefit from independent critique.
5. **“Design Drift” has three meanings**. Tool/schema drift is mechanically testable; truth drift between design decisions and shipped product needs visual/code comparison and approval. An observed-token snapshot is *not* the authoritative design system.
6. **“1:1 Figma” ≠ promise that screenshot is sufficient**. Desktop selected node, remote URL/node and screenshot-only inputs have different capabilities. Explicitly report missing source, asset permissions and intentional browser/accessibility deviations.
7. **“Responsive” ≠ mandatory mobile support**. Test declared supported viewports; device-specific demands apply only to supported products. Text zoom, keyboard and interaction must not be broken at the supported sizes.
8. **“VERIFIED” is scoped, never absolute**. State precisely what URL/route, behavior, viewport, locale, evidence and backend state was tested. A screenshot cannot validate persistence; an instrumented rAF trace is not aesthetic proof.
9. **“English instructions” ≠ English output UI**. Preserve user language, existing localized copy, CJK spacing, RTL when actually supported, source credits and legal notices. Do not translate identifiers or source code unnecessarily.
10. **“Protected visual rule” ≠ categorical ban on semantics**. H0 permits real breadcrumbs and meaningful brand narratives. S0 prohibits attached decorative card strips, not legitimate focus rings/progress/graph series with different roles.
11. **“Current guidelines” ≠ silent network access**. External design knowledge may evolve; when offline or unauthorized use the known local version and report freshness and coverage limitations.
12. **“Upstream Skill commands” ≠ MauForma dependency**. Source-specific hooks, autoplay demos, Claude/Gemini setup, Figma MCP APIs, React 19 features and PDF theme showrooms are optional workflows with host/framework/version prerequisites.

## Practical new workflow details adopted

- **Reconnaissance-first browser inspection**: discover real DOM and component roles before selecting browser actions; collect console/network issues alongside screenshots; server lifecycle is limited to the authorized project.
- **Context-specific locale checks**: apply international date/number formatting (Intl APIs where appropriate), allow paste, keep fields' error/focus behavior, check actual supported RTL scripts; no forced RTL on products that do not ship it.
- **Failure-state evidence**: error/permission/empty/loading/slow network and destructive actions should have task-appropriate recovery or confirmation/undo.
- **Dynamic source matching**: an empty style-search result means refine the query or report “no grounded match,” not select an unrelated style. A reference image is not authorization to copy an asset.
- **Scope-specific performance**: prioritize correctness, waterfalls, bundle impact, expensive render paths and composable cleanup based on the active framework and measured trace.
- **High-value demos vs real interactions**: a polished poster and animated showcase can be valid in marketing without proving actual user task execution.

## What this review does **not** verify

The upstream entrypoints and selected supporting references were inspected as currently accessible from the cited repositories on 2026-11-20. **Not every linked source file, dependency version or license was re-audited**, and future upstream content can change. The included MauForma local unit/Chromium smoke tests validate repository contracts and synthetic fixtures, not real user projects, aesthetic judgment or model inference. Instruction-language efficiency cannot be declared from bytes alone; controlled Agent A/B evaluation remains a separate task.

When a new upstream technique is proposed, require: **source → applicable trigger → actual user/project permission → exact observable behavior → exclusions and fallback → appropriate tool/evidence → matching English/Chinese semantics → test**. Only then make it a reusable rule.
