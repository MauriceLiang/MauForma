# Semantic Copy Hygiene · 小标题、辅助文案与英文副标的必要性审查

> v6.5：由用户提供的 RepoVantage 仓库分析页面截图归纳。目标是删掉**没有信息增量**的装饰文字，而不是让所有页面只剩一个标题。本规则优先用于 Operate / Read 类型的工作台、数据分析、设置页与管理后台。创意作品集、杂志、品牌官网可保留有品牌或叙事价值的辅助排版。

## 截图中可见的具体反例

| 用户截图中的文字 | 所在位置 / 问题 | 更合理的处理 |
| --- | --- | --- |
| `ANALYSIS STUDIO` | Logo 下方的英文副标，未展示实际产品子品牌/功能价值 | 若非正式品牌名称/产品线，直接删除；保留 `RepoVantage` |
| `仓库活动与协作 · 交互原型` | 主标题上方的功能重复 + 内部开发态标签，和页面用途已有交叉 | 如果需要 Demo 标识，用一个真实的 `演示数据` 状态标签；不要把“交互原型”当成美术导语 |
| `看见项目如何演进` | 巨大的抽象主标题，缺少明确当前任务信息 | 工作台首屏更适合 `仓库分析`、`开发活动` 或实际仓库名称；营销首页可以保留品牌主张 |
| `01 / 总览`、`先看活动，再沿证据往下读` | 自动编号 + 又一遍解释页面结构的口号式标题 | 若已由导航/区块标题说明用途，可直接保留 `开发活动`；编号仅用于真实步骤、排序、阅读章节 |
| `主图保留原生 ECharts tooltip、缩放与点选` | 把开发者实现备注暴露在产品界面 | 移到 PR、代码注释、QA 记录；只有用户需要知道怎样交互时才写成 `拖动缩放时间范围` 之类用户语言 |
| `所有数值均来自本地演示数据` 每个区域重复 | 数据来源状态重要，但多处重复使屏幕噪声上升 | 保留一个有意义的页面级来源提示；关键模拟指标按需显示 Demo 标记，并与真实数据区分 |
| `01 / 总览` 和导航中的 `总览` | 一眼可见的含义重复且容易伪造章节层级 | 删去重复小标题；如果跨多个页面有真实信息架构，需要正常面包屑或可访问 heading 层级 |

## 四道删除判断（Copy Necessity Gate）

每一个用户可见的 **eyebrow / kicker / overline / 英文副标题 / step index / slogan / 说明文字 / 技术提示** 都必须回答：

1. **独立含义**：删除它会失去什么导航定位、内容区别、真实业务状态、数据来源、专业意义或品牌识别？如果回答只是“更高级/更有设计感”，就应该删。
2. **是否重复**：它是否只是同一屏的主标题、面包屑、导航、Tab、卡片标题的转述？重复不必一律禁止：面包屑末级与 H1 同名本来合法；决定依据是是否具有**独立的导航功能**。
3. **是否面向用户**：这是用户需要看见的解释、状态、限制还是开发者的实现说明？例如“ECharts tooltip 保留原生”不属于用户界面内容。
4. **是否匹配页面**：产品发布页可以拥有情绪化 headline；进入仓库详情后，用户需要明确对象、指标和操作，没必要每一区都附一个英语小标签和一句诗意旁白。

**行动**：`keep`（保留并写出新增含义） / `merge`（合并到功能性标题或状态） / `move`（移至文档、帮助或 tooltip） / `delete`（删除，不以占位符补回）。在 `design-system/pages/*.md` 或截图审查中，只记录重要的保留/删除理由，不要为每个字符串制造官僚式表格。

## 默认的工作台标题层级

- **产品名**：RepoVantage；只有公司正式副品牌、用户已确认语言策略才增加英文副标。Logo 下方不要自动生成 `ANALYSIS STUDIO` / `SMART DASHBOARD`。
- **页标题（H1）**：仓库分析 / 项目比较 / 开发活动；一个明确任务。需要对象身份时显示仓库 `demo-labs/steady-core`。不要强制每页大字号“品牌宣言”。
- **区块标题（H2/H3）**：开发活动、Issue 处理、PR 协作、观察摘要等**功能性区分**。如果当前区已经只有一个图表，直接图表标题即可。
- **辅助文本**：仅解释采样范围、UTC、n 值、数据完整度、误差、限制、未完成状态等用户确实需要知道的信息。优先靠近对应数据。
- **面包屑**：真实可导航的层级可显示 `仓库 / steady-core`；不能用装饰性小字假装导航。
- **编号**：仅用于真实流程步骤/排序，例如 `步骤 1：选择仓库`、`01 / 审查问题`；不能机械给每一块贴 `01 / 总览`。

## 两个小标题合理存在的例子

- **阅读长文**：“研究方法 / 数据来源 / 局限性”帮助目录导航，具有实际检索意义。
- **品牌发布页**：产品系列名、上市季、主张标语承载辨识度或品牌语义；必要时可以大胆大字，非所有小标题都应消失。
- **图表标题 + 轴单位**：`开发活动` 和 `提交/次` 各自承担不同职责，不应误判为重复。
- **安全/权限状态**：`演示数据` / `仅管理员可修改` 必须在适当位置清楚出现，可用标签，不可为了“更干净”删除。

## 实施策略与 QA

- 先列出用户页面真正需要的内容，不因套用高端模板自动生成 kicker、双语副标题、章节数字、抽象口号。
- 对同一屏的标题做“新增信息审核”：保留 `仓库分析`、`开发活动`、`Issue 处理` 这类能定位任务的名称，避免 `可见未来 / 先观察，再发现 / 深入洞察` 等泛化套路。
- 检查自动翻译式二次标签（`USER MANAGEMENT` + `用户管理`）。如产品本身是中英双语、英文为专有名词或官方 tagline，可保留并有语言策略。
- 用 `scripts/audit_readability.py <src> --format json` 获取**仅供人工复核**的代码线索；脚本不能自动证明某文案是装饰性，也不得据此自动删内容。
- 提交前提供真实页面截图和一条简短结论：被删除的重复层级、保留的必要定位、开发者文案是否仍出现在用户界面。截图不可用须标注 NOT RUN。
