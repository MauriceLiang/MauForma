# Sidebar Color Discovery · 先看整页，再由用户决定配色

> **v6.6**：来自用户最新 RepoVantage 截图的反馈。侧栏已经没有多余竖条，但深蓝主背景、蓝色选择块与主区域偏亮灰底形成冷暖/亮度断层；截图并不能证明某一种颜色“客观错误”，却说明 Agent **不该未经确认就决定配色**。

## 必经 Color Choice Gate（新站 / 重设计 / 用户主动提出配色偏好）

### A. 先获取已有信息，不重问已提供的内容

阅读项目品牌资源、当前 Main/Topbar/Sidebar/Panel 的真实颜色、Logo 主色、设计 Tokens、dark/light 方案、用户以前的明确指令和页面截图。只在颜色方向未知、会影响决策时问一句：**“侧边栏想以什么颜色为主？可以直接说颜色名或 HEX；如果暂时没想法，我根据整个页面给你 2–3 套完整搭配看效果。”**

- 用户已经说“纯黑侧栏 / 白色导航 / 我喜欢绿色 / 用 #30414C” → 立刻尊重并采纳这个**颜色要求**，不再用三选一让用户重新同意，不擅自换回蓝紫。
- 用户只说“颜色不好看”，但没有要求哪一种颜色 → 先调查用途、已有主界面与品牌，提出 2–3 套**有明显区别的整页配色**，给出简洁理由与适用场景，问用户选择或给自定义颜色。选择前禁止把推荐色称为最终决定。
- 用户“你自由发挥”若**明确授权决定配色**：可以选择最合适的方案并记录 `delegated`；若仅委托布局或代码实现，不得推断为授权改变既有配色。用户指定某色优先级高于一般 Agent 设计委托。
- 已有品牌/已确认设计 → `inherited` / `confirmed` 延续，不反复要求投票；局部 Bug / 纯功能改动跳过完整访谈。
- 对用户给定的准确 HEX：**不能偷偷改色值或悄悄换色相**。有可读性问题时，可以调周围表面、文字、选中/焦点色并告知；如需要改用户指定的值，先解释冲突和选项，征得明确同意。

### B. 参考真实设计体系，但不机械复制

查看 `references/sidebar-color-reference-cases.md` 与 `assets/sidebar-color-directions.json`。至少对照来源中的两个不同方法论，例如 Linear 降低导航噪声、Carbon 独立语义状态、Primer 整页内容/侧栏分工、shadcn/ui 的 sidebar tokens、Atlassian 的单一 Token 来源。**案例颜色为 MauForma 自创演示，不是官方产品色值截图采样**。

只挑与当前项目匹配的 2–3 组候选，讲清：

1. **侧栏底色**（深/浅/中性/用户指定）；**主内容底色**和顶部栏怎么衔接；
2. 选中态、默认与悬停文字、图标、边界、焦点的对比；主色在哪里使用、哪里不使用；
3. 哪组适合当前项目类型、为什么，长期使用的权衡；
4. 浅/深模式和数据图表与页面其余色彩协调策略；不能只给一张孤立的侧栏色块。

**必要原则：让用户比较“整个页面中的侧栏”而不是五张单独侧栏图片。** 本仓库 `assets/sidebar-color-preview.html` 展示原创五组配色及整个工作台关系，仅用于参考；Agent 向真实用户展示时通常筛选 2–3 组，不要一次推五种。

### C. 最终确认与真实实施

- 给出 “推荐 A（理由）、B（优劣）、自定义颜色（支持中文/HEX/截图）” 的选择入口。**Agent 推荐不是用户确认。**
- 将 `design-system/sidebar-color-decision.json` 存为项目决策（形状见 `assets/sidebar-color-decision.schema.json`）。`status=pending` 时未批准配色，不能当成已经选好来重写真实全站颜色。
- 用户选择后写入 `status=approved`、`source=confirmed`、选择的候选/自定义颜色和用户原话；明确委托才能用 `delegated`；继承已有已确认配置可用 `inherited`。不得伪造用户原话。
- 只使用已有主题变量或统一 `MASTER`，不要为侧栏建立独立、脱节的品牌色系统。侧栏 Tokens 可有独立角色，但来源仍是同一个项目主题。
- 实际实现必须检查 **Sidebar ↔ Topbar ↔ Main ↔ Card ↔ Chart** 的颜色温度、表面层级、过渡边界、文字对比、图表序列角色；若旧页面未改，不能只改 sidebar 后声称整站协调。
- 在真实浏览器查看宽屏与窄屏、light/dark、hover/selected/focus、颜色对比与 200% 字体放大。静态色值校验**无法证明审美和实际配色协调**。

## 用户指定“很难读”的颜色怎么办？

例如要求纯黄色侧栏：**黄色仍然是用户要求，不能悄悄替换成深蓝**。应提出亮黄侧栏 + 深色文字与适合的主区域，给出示例并测实际对比；如果用户还要求浅黄上的白字造成对比不足，就指出冲突，建议保留黄底而更换字色，或让用户明确认可更深的黄色选中状态。不得违背用户明确选择，也不把不可读界面伪称“已通过”。

## 决策权边界

- 用户决定 **要什么主色、允许什么整体视觉气质**。
- Agent 负责 **推荐、解释利弊、做可访问性协调、产生 Token 与验证**。
- 若用户拒绝 Agent 的首选方案，Agent 应采用用户指定方向重新做整页协调，不以“设计师认为不够高级”拒绝。
- 只在缺少阻断开发的颜色决策时问一次关键问题；不通过反复问卷拖慢工作。没有明确颜色授权时，可先继续不依赖色值的布局、结构和组件工作，**不要默认把推荐样板写入最终主题**。

参考对话见 `examples/sidebar-color-discovery-dialogues.md`；具体记录与验证用 `scripts/validate_sidebar_color_decision.py`。
