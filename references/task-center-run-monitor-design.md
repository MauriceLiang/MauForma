# Task Center & Run Monitor UX · 任务执行工作台，不是堆数字的仪表盘（v6.11）

> 适用：异步任务、采集任务、CI/CD、批处理、导入导出、Agent Runs、部署或后台作业监控。若任务是“人员分配/里程碑/Kanban”，可参考 Linear，但**不应直接把人工任务管理的看板模式照搬到自动执行作业**。
>
> 证据：用户于 2026-11-04 提交 RepoVantage 任务中心截图。截图显示左侧“任务状态”一张纵向统计卡，占去显著宽度，右侧“任务记录”用很宽的长列表但每条信息集中在左半部分；“进度百分比未知，当前显示阶段状态”逐行重复。截图不能证明 API 未工作或按钮不可点击，必须实际运行时验证。

## 成熟产品研究（借鉴任务模式，**不是照搬品牌视觉**）

| 参考 | 借鉴的能力 | 何时适用 | 不照搬的原因 |
| --- | --- | --- | --- |
| [GitHub Actions – workflow run history](https://docs.github.com/en/actions/monitoring-and-troubleshooting-workflows/monitoring-workflows/viewing-workflow-run-history) | 运行列表先给状态/对象/时间，选中任务进入步骤和日志 | 一次性/周期性后台任务 | 不需要照抄其复杂仓库/工作流导航 |
| [GitLab Pipelines](https://docs.gitlab.com/ci/pipelines/) 与 [GitLab Jobs](https://docs.gitlab.com/ci/jobs/) | 状态筛选、阶段概览、失败优先定位、合法重试/取消 | 多阶段采集/流水线 | 若只是单步骤采集不要画虚构 DAG |
| [Trigger.dev Runs](https://trigger.dev/changelog/live-runs-page) 与 [Run Inspector](https://trigger.dev/changelog/run-page-inspector) | 状态原位更新、新任务提示、详情放时间线/日志/输入输出 | 高频异步作业、父子任务 | 不必照搬它的所有工程调试元数据 |
| [Inngest – inspect events and runs](https://www.inngest.com/docs/platform-and-operations/inspect-events-and-runs) | 从失败追到触发事件/失败步骤/重试历史 | 有明确可诊断事件的复杂工作流 | 不把技术事件 payload 长驻列表 |
| [Vercel – deployments](https://vercel.com/docs/deployments/managing-deployments) | 清楚的状态/时间筛选、一次运行的详细页、按条件重新部署 | 批量运行、版本化对象 | 任务重试不能等同于重新部署 |
| [Linear – display options](https://linear.app/docs/display-options) 与 [Filters](https://linear.app/docs/filters) | 列表显示字段按任务需要可调整，状态分组/优先级排序、过滤入口 | 用户需要快速扫描、定位/批量处理 | Linear 是人工任务管理，不是机器 Run 进度模型 |

共性：**一行足以回答“什么任务 / 当前怎样 / 什么时候 / 下一步做什么”**，复杂步骤和日志进入详情视图；状态/筛选/信息密度是效率工具，而非装饰性卡片。引用页面即研究依据，不能假定它们都使用完全相同的布局。

## Gate T0 · 先定位工作类型与主要用户任务

`run_monitor`：自动运行、排队、状态变化与重试；`human_tasks`：人员待办、优先级、指派、截止期；`mixed`：两者并存但要明确区分。

Run Monitor 的典型问题：哪一项失败/卡住？还在运行吗？进展如何？我能做什么？去哪看失败原因？日志是否能定位问题？如果只给任务数 3/3/1，却需要滚一大屏查故障，就没有解决核心任务。

## Gate T1 · 内容分层和信息密度

1. **页头**：`任务中心` + 必要作用域（仓库/工作区），右侧一项刷新（可给出最后更新时刻与自动更新状态）。不是长篇“Mock 服务怎样处理”的说明。
2. **状态概览**：优先使用紧凑 Filter Tabs 或 Segmented Control（`全部 / 运行中 / 等待中 / 需处理 / 已完成`），**状态计数同时作为可操作筛选器**；只有需要历史趋势/健康指标时才考虑独立统计卡。不能将这几个数字放入永久占 1/4 主区域的超高卡片。
3. **任务主列表**：占据主要内容宽度，用**表格/紧凑行**（适量留白、可读）布局，列例如「任务/对象（含任务类型）·状态·进度/当前阶段·最近更新·操作」。信息少时不要让整行撑到 110px 并重复多句相同说明。
4. **优先级**：默认让 `requires_attention`、运行中、等待中比历史完成更容易找到；也允许“最近更新”等用户选择排序。不要每行都放大色块、警告条或不必要的前缀。
5. **详情**：按需打开 Run Detail（抽屉/页面/展开行，按用户工作流选），包含触发信息、时间线、当前步骤、实际日志、失败原因与重试记录。列表默认不用全文展开。
6. **状态区分**：排队（queued）、运行中（running）、等待依赖（waiting）、部分完成（partial）、失败（failed）、阻塞（blocked）、完成（succeeded）、取消（canceled）都是不同运行语义。可将多个状态汇总到用户可读的 Filter，但具体标签不宜模糊成“关注中”或统一“处理中”。
7. **空态**：没有任务时提供可执行的下一步；过滤无结果时提示清除条件；API 加载/失败不能直接被当成 0 个完成任务。
8. **布局**：桌面可稳定列对齐；手机切换成结构化 task rows/cards，不靠缩成 10px 字体塞完 5 列。超过一屏可自然滚到底，需符合 v6.9。

## Gate T2 · 一行任务的数据契约

来自后端的 `task_id` 唯一不可随意重用。`repository`、`task_type`、`state`、`started_at` / `updated_at`、`retryable`、`details_route` 等字段须有明确含义。时间排序使用正确时间戳，显示格式按用户所在地/时区，不将 Mock 固定时间当“刚刚”。

- **进度**：`completed`/`total` 只有同一单位、`total > 0` 且是可确认总体时才能转百分比；`1200/6800` 是约 17.6%，但若“总量可动态变化”应声明预计/不完整。仅有阶段文字时，显示“正在分析”与可用日志入口，**绝不捏造 42%、ETA 或固定进度条**。
- **缺失**：`progress: null` ≠ 0%；`error: null` ≠ “未知错误”；`updated_at: null` ≠ “刚刚”。
- **状态**：过滤统计由同一列表数据推导；状态和操作不冲突；状态是 completed 不等于“已覆盖全部 GitHub 数据”。
- **需处理**：对`partial/failed/blocked`等明确可行动失败可进入 Attention 分组；是否提供重试，取决于 `retryable`、权限、后端操作支持和具体原因，不能对所有异常展示假按钮。阻塞的认证/口径错误通常应先提供修复入口。
- **重试**：用户触发 → 审核当前 Run/最新状态与权限 → 请求后端 → 根据响应刷新状态。不能点击按钮就假装服务器已经重试成功；乐观状态要有回滚和错误说明。重复请求按后端支持采用幂等处理/禁用。
- **取消/暂停**：只有服务端支持且用户拥有权限才展示。取消若不可逆或影响后续任务，给出具体影响说明，不设计装饰性的操作按钮。
- **实时更新**：轮询、SSE/WebSocket 或手动刷新均可；需要最后更新信息与连接/失联状态。刷新时列表不应意外跳回顶部、清空筛选、改变选中对象；有新任务可提示，不必强行重排用户视线。
- **行记录**：关键失败原因/下一步可就近显示一句；不要每条任务都重复“进度百分比未知，当前显示阶段状态”。

## Gate T3 · 交互、可发现与排序

建议默认支持：状态切换、按仓库/任务类型搜索或过滤、明确的时间/重要程度排序、查看详情、合法的重试，必要时取消；**不要求所有产品都增加批量操作、Kanban、分页、自动更新**。这取决于实际任务数、权限与用户要完成的工作。

- 状态筛选的数量与可见任务匹配；如果分页、搜索范围或服务端聚合不同，明确显示“当前页”还是“全部”。
- 检查任务行本体是否可点与内部按钮是否冲突；按 Enter/Space/Tab 能访问，不以仅有 hover 才出现的操作为唯一途径。
- 独立详情/操作弹窗打开后需保持正确焦点、返回上下文与筛选；错误状态有可理解的解决路径。
- `completed` 列表可以保留历史入口，但默认不要让旧记录占用首要区域压住失败。

## Gate T4 · 布局与视觉纪律

**列表对齐、列密度、任务层级**：任务身份比状态标签更重要还是需要行动更重要？按当前工作流判断。使用一套稳定行高/列轨；状态颜色只代表状态，不额外生成每行大色块和整排图标；同级任务行的左边缘、字段基线和操作列对齐。

**不要把所有任务信息填满宽度**：合理的内容最大宽度与可读列宽优于凭空撑满；剩余宽度可分给可筛选操作或真正的进度信息，不要靠重复说明增加视觉存在感。

**两种产品类型例外**：如果用户要一个「任务异常排查中心」，侧边紧凑筛选栏可能合理；如果是单一任务引导页，一个大进度视图也合理。问题不在于永远禁止 Side Panel，而在于该侧栏是否提供独立、频繁的筛选/分析价值。

## Gate T5 · 浏览器验收

- 在桌面（例如 1440×900 和 1280×720）与窄屏（例如 390×844）查看列表：任务是否能快速扫描，主操作/状态/进度清晰，行/列稳定对齐；
- 状态 Filter 与实际行数一致；搜索筛选后计数语义不误导；
- 部分完成/失败/阻塞的操作不同；重试不得错误出现在已完成/排队等非许可任务；
- 有可计算的进度才渲染有百分比的进度条；未知进度为不确定状态/当前阶段；
- 行展开/详情可用且不会破坏布局；长仓库名、长错误信息换行/省略能全文查看；
- 窄屏所有任务可访问、可滚到最后，按钮不被固定栏遮挡；
- 已运行自动化只证明被测试的状态。真实服务端的重试、权限、日志和实时数据仍需 API/E2E 测试；截图/Mock 不能证明它们有效。
